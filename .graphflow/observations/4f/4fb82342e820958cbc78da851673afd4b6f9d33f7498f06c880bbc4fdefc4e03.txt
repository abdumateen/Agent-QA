1: # MCP tools
2: 
3: Agent QA exposes fourteen MCP tools through a separate server process. Each
4: tool forwards its operation to the core REST service at
5: `http://127.0.0.1:8765`.
6: 
7: The MCP process does not access the database or start the core service.
8: 
9: ## Start the services
10: 
11: From the repository root, start the core in one terminal:
12: 
13: ```bash
14: poetry --directory core install
15: poetry --directory core run agent-qa-core
16: ```
17: 
18: In another terminal, start the stdio MCP server:
19: 
20: ```bash
21: poetry --directory core run agent-qa-mcp --transport stdio
22: ```
23: 
24: An MCP client normally launches and manages the stdio process. Standard output
25: is reserved for protocol messages; logs go to stderr and the configured log
26: file.
27: 
28: For SSE, start a persistent server:
29: 
30: ```bash
31: poetry --directory core run agent-qa-mcp --transport sse --port 8766
32: ```
33: 
34: The SSE endpoint is `http://127.0.0.1:8766/sse`. The listener remains bound to
35: `127.0.0.1`.
36: 
37: ### Configuration
38: 
39: | Setting | Default | Description |
40: | --- | --- | --- |
41: | `AGENT_QA_MCP_TRANSPORT` | `stdio` | `stdio` or `sse` |
42: | `AGENT_QA_MCP_PORT` | `8766` | SSE port; must differ from `8765` |
43: | `AGENT_QA_LOG_DIR` | `~/.agent-qa/logs` | Process log directory |
44: | `AGENT_QA_LOG_LEVEL` | `INFO` | Logging level |
45: 
46: Command-line transport and port options override environment settings.
47: 
48: Use separate log directories when core and MCP run directly on the same
49: machine. Rotating file handlers do not coordinate rotation across processes.
50: 
51: ### Client configuration
52: 
53: When `agent-qa-mcp` is installed on the client process's executable search path:
54: 
55: ```json
56: {
57:   "mcpServers": {
58:     "agent-qa": {
59:       "command": "agent-qa-mcp",
60:       "args": ["--transport", "stdio"],
61:       "env": {
62:         "AGENT_QA_LOG_DIR": "~/.agent-qa/mcp-logs"
63:       }
64:     }
65:   }
66: }
67: ```
68: 
69: A Poetry installation keeps executables inside its environment. If the client
70: cannot locate the executable, configure it to launch Poetry from the core
71: directory or use the executable's absolute path from that environment.
72: 
73: Database settings belong to the running core process. Setting
74: `AGENT_QA_DB_PATH` only on the MCP process does not change the core's database.
75: 
76: ## Shared conventions
77: 
78: - Content and schemas are JSON objects.
79: - Tags are optional arrays of strings.
80: - Empty tags, commas within tags, and control characters are rejected.
81: - Limits are integers between `1` and `1000`.
82: - Durations are finite, nonnegative seconds.
83: - Timestamps use UTC ISO 8601 strings ending in `Z`.
84: - Fixture names are unique across the database, not scoped by type.
85: - Test aggregates are identified by both test name and framework.
86: - Missing singular records produce tool errors; empty list queries return `[]`.
87: 
88: The return types below describe the logical tool result. MCP clients may
89: display these results through text content or structured content according to
90: the SDK and client implementation.
91: 
92: ## Tool reference
93: 
94: ### 1. `get_fixture`
95: 
96: Retrieve a named fixture, optionally requiring an exact type.
97: 
98: | Parameter | Type | Default |
99: | --- | --- | --- |
100: | `name` | string | required |
101: | `type` | string or null | null |
102: 
103: Returns a fixture object containing `id`, `name`, `type`, `content`, `hash`,
104: `tags`, `created_at`, and `updated_at`.
105: 
106: ```json
107: {
108:   "name": "pending-order",
109:   "type": "http-response"
110: }
111: ```
112: 
113: An unknown name or mismatched type produces a tool error.
114: 
115: ### 2. `remember_fixture`
116: 
117: Create or replace a fixture.
118: 
119: | Parameter | Type | Default |
120: | --- | --- | --- |
121: | `name` | string | required |
122: | `type` | string | required |
123: | `content` | object | required |
124: | `tags` | string array or null | null |
125: 
126: Returns the stored fixture object.
127: 
128: ```json
129: {
130:   "name": "pending-order",
131:   "type": "http-response",
132:   "content": {
133:     "order_id": 42,
134:     "state": "pending"
135:   },
136:   "tags": ["orders", "integration"]
137: }
138: ```
139: 
140: An existing name retains its ID and creation timestamp. Mutable fields are
141: replaced, including tags. Omitting tags clears them.
142: 
143: The hash is SHA-256 over canonical JSON content, independent of object key
144: ordering.
145: 
146: ### 3. `list_fixtures`
147: 
148: List fixtures ordered by update timestamp and ID, newest first.
149: 
150: | Parameter | Type | Default |
151: | --- | --- | --- |
152: | `tag` | string or null | null |
153: | `limit` | integer | 50 |
154: 
155: Returns an array of fixture objects. Tag filtering matches a complete,
156: case-sensitive tag.
157: 
158: ```json
159: {
160:   "tag": "orders",
161:   "limit": 20
162: }
163: ```
164: 
165: ### 4. `get_api_contract`
166: 
167: Retrieve a contract by endpoint, method, and optional response status.
168: 
169: | Parameter | Type | Default |
170: | --- | --- | --- |
171: | `endpoint` | string | required |
172: | `method` | string | required |
173: | `status_code` | integer or null | null |
174: 
175: Returns an object containing `id`, `endpoint`, `method`, `request_schema`,
176: `response_schema`, `status_code`, `tags`, `created_at`, and `updated_at`.
177: 
178: ```json
179: {
180:   "endpoint": "/orders",
181:   "method": "POST",
182:   "status_code": 201
183: }
184: ```
185: 
186: Methods are normalized to uppercase. When status is omitted, the lowest
187: stored status code is selected.
188: 
189: Pass the endpoint literally; the MCP server handles URL encoding.
190: 
191: ### 5. `remember_api_contract`
192: 
193: Create or replace a contract identified by endpoint, method, and status code.
194: 
195: | Parameter | Type | Default |
196: | --- | --- | --- |
197: | `endpoint` | string | required |
198: | `method` | string | required |
199: | `request_schema` | object | required |
200: | `response_schema` | object | required |
201: | `status_code` | integer | required |
202: | `tags` | string array or null | null |
203: 
204: Returns the stored contract object. Status codes must be between `100` and
205: `599`. Both schema documents are checked as JSON Schema Draft 2020-12.
206: 
207: ```json
208: {
209:   "endpoint": "/orders",
210:   "method": "POST",
211:   "request_schema": {
212:     "type": "object",
213:     "properties": {
214:       "sku": {"type": "string", "minLength": 1},
215:       "quantity": {"type": "integer", "minimum": 1}
216:     },
217:     "required": ["sku", "quantity"],
218:     "additionalProperties": false
219:   },
220:   "response_schema": {
221:     "type": "object",
222:     "properties": {
223:       "order_id": {"type": "integer", "minimum": 1}
224:     },
225:     "required": ["order_id"],
226:     "additionalProperties": false
227:   },
228:   "status_code": 201,
229:   "tags": ["orders"]
230: }
231: ```
232: 
233: An omitted dialect declaration defaults to Draft 2020-12.
234: 
235: ### 6. `remember_failure`
236: 
237: Append a distinct failure occurrence.
238: 
239: | Parameter | Type | Default |
240: | --- | --- | --- |
241: | `test_name` | string | required |
242: | `error_message` | string | required |
243: | `stack_trace` | string | required |
244: | `root_cause` | string | required |
245: | `fix` | string | required |
246: | `tags` | string array or null | null |
247: 
248: Returns an object containing `id`, `test_name`, `error_message`, `stack_trace`,
249: `root_cause`, `fix`, `resolved`, `tags`, `created_at`, and `resolved_at`.
250: 
251: ```json
252: {
253:   "test_name": "tests/test_orders.py::test_create_order",
254:   "error_message": "Expected status 201, received 503",
255:   "stack_trace": "AssertionError: 503 != 201",
256:   "root_cause": "",
257:   "fix": "",
258:   "tags": ["orders"]
259: }
260: ```
261: 
262: Unknown stack traces, diagnoses, and fixes may be empty strings. Test names and
263: error messages must be nonempty.
264: 
265: New records are unresolved even when a diagnosis and fix are supplied.
266: Repeated calls create separate occurrences rather than updating one record.
267: 
268: ### 7. `get_failure`
269: 
270: List failures for an exact test name.
271: 
272: | Parameter | Type | Default |
273: | --- | --- | --- |
274: | `test_name` | string | required |
275: | `error_pattern` | string or null | null |
276: 
277: Returns failure objects ordered newest first.
278: 
279: ```json
280: {
281:   "test_name": "tests/test_orders.py::test_create_order",
282:   "error_pattern": "503"
283: }
284: ```
285: 
286: The error pattern is a case-sensitive literal substring, not a regular
287: expression or SQL pattern.
288: 
289: ### 8. `resolve_failure`
290: 
291: Resolve a failure using a nonempty diagnosis and corrective action.
292: 
293: | Parameter | Type | Default |
294: | --- | --- | --- |
295: | `failure_id` | positive integer | required |
296: | `root_cause` | string | required |
297: | `fix` | string | required |
298: 
299: Returns the updated failure object.
300: 
301: ```json
302: {
303:   "failure_id": 1,
304:   "root_cause": "Requests arrived before service readiness",
305:   "fix": "Wait for a successful readiness check before sending requests"
306: }
307: ```
308: 
309: Use an ID returned by `remember_failure` or `get_failure`. Repeated resolution
310: updates the diagnosis and fix but preserves the first resolution timestamp.
311: 
312: ### 9. `suggest_test`
313: 
314: Retrieve stored memories relevant to a proposed test.
315: 
316: | Parameter | Type | Default |
317: | --- | --- | --- |
318: | `description` | string | required |
319: | `limit` | integer | 10 |
320: 
321: Returns ranked search results with `source`, `score`, and `record`.
322: 
323: ```json
324: {
325:   "description": "Order creation when the service is not ready",
326:   "limit": 10
327: }
328: ```
329: 
330: This tool searches existing memory. It does not produce new test code.
331: 
332: ### 10. `record_test_run`
333: 
334: Record an execution and atomically refresh its aggregate.
335: 
336: | Parameter | Type | Default |
337: | --- | --- | --- |
338: | `test_name` | string | required |
339: | `framework` | string | required |
340: | `status` | string | required |
341: | `duration` | number | required |
342: | `error_message` | string or null | null |
343: 
344: Accepted statuses are `passed`, `failed`, `error`, and `skipped`.
345: 
346: ```json
347: {
348:   "test_name": "tests/test_orders.py::test_create_order",
349:   "framework": "pytest",
350:   "status": "failed",
351:   "duration": 0.184,
352:   "error_message": "Expected status 201, received 503"
353: }
354: ```
355: 
356: Returns a test-run object containing `id`, `test_name`, `framework`, `status`,
357: `duration`, `error_message`, and `timestamp`.
358: 
359: This operation does not create a failure record. Use `remember_failure`
360: separately when diagnostic history is needed.
361: 
362: ### 11. `get_flaky_tests`
363: 
364: List nonempty histories meeting an inclusive failure threshold.
365: 
366: | Parameter | Type | Default |
367: | --- | --- | --- |
368: | `threshold` | number | 0.3 |
369: 
370: The threshold must be finite and between zero and one.
371: 
372: ```json
373: {
374:   "threshold": 0.5
375: }
376: ```
377: 
378: Returns aggregate objects containing:
379: 
380: - `test_name` and `framework`
381: - `run_count` and `fail_count`
382: - `flaky_score`
383: - `last_updated`
384: - `quarantined`
385: - `quarantine_reason`
386: - `quarantined_at`
387: 
388: The score is `fail_count / run_count`. Failed and error executions contribute
389: to the numerator; every recorded execution contributes to the denominator.
390: 
391: At threshold zero, all nonempty histories qualify. Consistently failing tests
392: also qualify: this is a failure-frequency metric.
393: 
394: The MCP default is explicitly `0.3`. Changing the core's environment threshold
395: does not change this tool's default argument.
396: 
397: ### 12. `quarantine_test`
398: 
399: Persist a quarantine decision for a test with recorded history.
400: 
401: | Parameter | Type | Default |
402: | --- | --- | --- |
403: | `test_name` | string | required |
404: | `framework` | string | required |
405: | `reason` | string | required |
406: 
407: Returns the updated aggregate object.
408: 
409: ```json
410: {
411:   "test_name": "tests/test_orders.py::test_create_order",
412:   "framework": "pytest",
413:   "reason": "Investigating intermittent readiness failures"
414: }
415: ```
416: 
417: Quarantine does not skip tests or alter execution counts. Repeating the call
418: updates its reason and decision timestamp.
419: 
420: ### 13. `search_memory`
421: 
422: Search fixtures, contracts, and failures.
423: 
424: | Parameter | Type | Default |
425: | --- | --- | --- |
426: | `query` | string | required |
427: | `limit` | integer | 20 |
428: 
429: ```json
430: {
431:   "query": "orders readiness timeout",
432:   "limit": 20
433: }
434: ```
435: 
436: Returns an array whose entries contain:
437: 
438: | Field | Description |
439: | --- | --- |
440: | `source` | `fixtures`, `api_contracts`, or `failures` |
441: | `score` | Negated FTS5 BM25 rank; larger is more relevant |
442: | `record` | Complete source record |
443: 
444: Queries accept at most 4096 characters and 128 distinct searchable terms.
445: Terms are combined with `OR`; raw FTS5 operators are treated as ordinary text.
446: No matching records produces an empty array.
447: 
448: ### 14. `health`
449: 
450: Check core connectivity and database access. Takes no arguments.
451: 
452: Returns:
453: 
454: ```json
455: {
456:   "status": "ok",
457:   "version": "0.1.0"
458: }
459: ```

480: ## Errors and retries
481: 
482: Requests use five-second HTTP timeouts and retry connection-establishment
483: failures once. Read timeouts and HTTP error responses are not retried.
484: 
485: Unsuccessful HTTP responses become tool errors reporting the HTTP status.
486: Invalid JSON or an unexpected response shape also produces a tool error.
487: 
488: After an ambiguous write failure, inspect stored state before repeating the
489: operation. Failure and test-run writes append records and have no idempotency
490: key, so blindly repeating them can duplicate history.
491: 
492: For endpoint validation details, see [rest-api.md](rest-api.md).
